# Validation and test tooling

How mlat-server-rs was checked against the original Python mlat-server, and how you can repeat or extend that. None of this is needed to run the server.

The approach: take a **capture of real receiver traffic**, replay it into both servers, and compare what comes out (positions, state files, CPU). Underneath that, each numerical stage of the port was compared with the real Python code on recorded inputs.

> **Privacy.** A capture contains receiver names, UUIDs, IP addresses and coordinates. Never publish one. `*.pcap` and `*.jsonl` are in `.gitignore`. Fixtures in `crates/mlat-core/tests/fixtures` are synthetic: generated by calling the Python code on random inputs.

## What is here

| Path | What it is |
|---|---|
| `crates/mlat-tools` | `mlat-capture`: `extract` (pcap to events) and `replay` (events into a live server, with `--udp` for the UDP transport). Also the benchmarks `pipebench`, `syncbench` and `examples/ingest_bench.rs`. |
| `crates/mlat-core/tests` | Golden tests: the Rust stages against values produced by the Python code (Mode S decoding, solver, normalisation, Kalman filter, resolve, SBS formatting, partitioning). |
| `crates/mlat-core/examples`, `crates/mlat-proto/examples` | Small diagnostics used while matching MINPACK step by step; `xcheck` checks the zlib framing against Python's. |
| `testbed/Dockerfile` | Builds a throwaway copy of the Python server, the reference. |
| `testbed/run-baseline.sh` | Replays a capture into the Python (default) or Rust server in Docker and keeps its outputs and CPU time. |
| `testbed/py_sync_ref.py`, `py_pipeline_ref.py` | Run the *real* Python coordinator on a capture with a virtual clock (no sockets), so a re-implementation can be compared result by result. |
| `testbed/record_wrap.py` | Runs the unmodified Python server while logging the inputs and outputs of its numerical core, as golden data. |
| `testbed/gen_modes_golden.py`, `gen_sbs_golden.py` | Generate the fixtures from the real compiled modules. |
| `testbed/compare_results.py`, `compare_pipeline.py`, `compare_state_files.py`, `score_adsb.py` | Compare positions, result streams, state-file shape, and accuracy against ADS-B truth. |
| `testbed/rerun_*.py`, `first_step.py`, `resid.py`, `trace_leastsq.py`, `gc_wrap.py`, `sbs_tap.py` | Helpers used while debugging individual stages. |

## 1. Unit and golden tests

    cargo test --release

These need nothing else: the fixtures ship in the repo. A few tests replay larger recordings of the Python server's numerical core. They read the directory in `MLAT_REC_DIR` and **skip if it is absent**, so a plain checkout runs the fixture-based ones only. Make such a recording with `RECORD=1 testbed/run-baseline.sh ...` (below); it lands under `<out>/rec`.

For a bit-exact solver comparison, build on Linux with the `glibc-pow` feature (the C library's `pow()` differs from `x*x` in about 1 case in 1,200, and Python uses the former):

    cargo test --release -p mlat-core --features glibc-pow

## 2. Capture and replay

1. Record on the server host, starting `tcpdump` before receivers connect (each zlib stream is continuous per connection, so every connection's SYN must be in the capture; restart the server after starting the capture if needed):

       tcpdump -i eth0 -s 0 -nn -B 16384 -w mlat-capture.pcap 'tcp port 31090'

2. Decode it to an event file:

       cargo run --release -p mlat-tools --bin mlat-capture -- extract mlat-capture.pcap -o capture.jsonl

3. Replay it. Every captured receiver becomes a live connection (user and uuid prefixed so it can never clash with a real one), sending its messages at their original times, grouped as in the original packets. Only loopback and private targets are allowed unless you pass `--allow-public`. Never point this at a production server.

       cargo run --release -p mlat-tools --bin mlat-capture -- replay capture.jsonl --target 127.0.0.1:31090 --results results.jsonl [--udp] [--max-secs N]

## 3. Compare against the Python server

Build the Python reference from a checkout of the original (the Docker build context is that checkout):

    git clone https://github.com/wiedehopf/mlat-server /tmp/mlat-python
    docker build -f testbed/Dockerfile -t mlat-baseline:local /tmp/mlat-python
    # for bit-comparable numerics, a build without fused multiply-add:
    docker build -f testbed/Dockerfile --build-arg EXTRA_CFLAGS=-ffp-contract=off -t mlat-baseline:nofma /tmp/mlat-python

Build the Linux Rust server the script runs:

    mkdir -p testbed/rust-bin
    docker run --rm -v $PWD:/src -e CARGO_TARGET_DIR=/tmp/t -w /src rust:1 sh -c \
      "cargo build --release -p mlat-server --features glibc-pow && cp /tmp/t/release/mlat-server-rs /src/testbed/rust-bin/"

Run both servers on the same capture (about the capture's duration each) and compare:

    testbed/run-baseline.sh py   31200 capture.jsonl OUT            # Python
    RUST_SERVER=1 testbed/run-baseline.sh rs 31201 capture.jsonl OUT   # Rust

    testbed/compare_results.py   OUT/py/results.jsonl OUT/rs/results.jsonl
    testbed/score_adsb.py        capture.jsonl OUT/py/sbs.txt OUT/rs/sbs.txt
    cat OUT/*/cpu.txt            # CPU seconds from the container's cgroup

`run-baseline.sh` options (environment): `RUST_SERVER=1`, `SNAPSHOTS=1` (copies the state files periodically, which is what `compare_state_files.py PYDIR RUSTDIR` wants, since the final files are empty once every receiver has disconnected), `RECORD=1`, `GC_OFF=1`, `PROFILE=1`.

`score_adsb.py` takes ADS-B truth from the DF17 position messages in the receivers' own `sync` messages, decoded with CPR relative to the reporting receiver, and scores the Basestation positions of aircraft that were both multilaterated and broadcasting ADS-B. It reads the replay start time from the `replay-report.txt` beside each `sbs.txt`. It fits one common timing offset for the truth (receivers deliver sync messages late), so read the absolute figure as an upper bound and compare the servers with each other.

## 4. Deterministic, offline comparison

For a repeatable check of the whole pipeline without sockets or real time:

    docker run --rm --entrypoint python3 -v $PWD:/data -v $PWD/testbed:/h mlat-baseline:nofma \
        /h/py_pipeline_ref.py /data/capture.jsonl /data/pipeline-golden.jsonl
    cargo run --release -p mlat-tools --bin pipebench -- capture.jsonl rust.jsonl --threads 1
    testbed/compare_pipeline.py pipeline-golden.jsonl rust.jsonl

`pipebench` runs deterministic by default (every observation waits for the pipeline to catch up); `--fast` runs it free, as in production. `py_sync_ref.py` and `syncbench` do the same for the clock-sync stage alone (`syncbench capture.jsonl --golden golden.jsonl --threads 1`).

## Results

On one 14-minute capture of about 140 receivers (about 2.2 million messages):

* **Whole pipeline, deterministic, on Linux with `glibc-pow`:** all 1,830 results reproduced by the Rust pipeline.
* **Clock sync stage, one matcher and one pairer:** identical to Python (max relative error 2e-16). With more threads, shared counters are not sequenced, so results are statistically equivalent, not identical.
* **Solver:** on 5,701 recorded solves, identical status, evaluation count, solution and covariance on x86-64.
* **Kalman filter:** against 1,845 recorded updates for 53 aircraft, no discrete differences (acquisitions, lost locks, outlier gates, resets); position within 9e-9 m.
* **SBS lines:** 6,000 generated cases identical to the real `BasestationClient.write_result`.
* **Whole server, live replay, Docker:** 93% of positions have a counterpart in the other server's output, median difference 12 m (two runs of the Python server against itself: 5-6 m). CPU for the whole replay: 148 s Python, 60 s Rust. Against ADS-B truth, median error 107 m (Python) and 105 m (Rust) on a small sample of 68 and 92 positions.
* **Offline engine benchmark:** one feeding thread pushing the whole capture through the engine as fast as it can: 1.6 s at one engine thread, 2.4 s at two, 3.3 s at four. This is the reason more engine threads are not claimed to help at this size.

## Limits of this validation

* One capture, one network, receivers running mlat-client 0.4.2.
* Bit-exact claims hold on Linux with `glibc-pow`; on macOS (Apple libm) a few altitude-constrained solves differ in the last bit. scipy on arm64 and x86-64 also differ in about 1 solve in 1,500.
* The live-server comparison is statistical, since the original's forced-mlat timing is random.
* The ADS-B truth is crude (see above) and the sample is small.
* The scripts were written on macOS with Docker Desktop; expect to adjust paths on other setups. The Python reference imports the original from `/opt/mlat-server` inside its image.

## Things worth knowing if you extend it

* `serde_json` needs the `float_roundtrip` feature wherever inputs must be bit-exact. The default parser mis-rounds some 17-digit decimals, and the solver's finite-difference Jacobian amplifies that by about 1e8.
* Python 3.12+ `sum()` uses compensated summation; don't compare against it naively.
* scipy's `minimum_spanning_tree` lets a zero-weight edge join two nodes while building the tree and then erases it from the result.
* The original has several quirks the port reproduces on purpose (integer division in the drift filter, `_update_offset` always seeing zero elapsed time, the order of the clock-jump reset, `MIN_ALT`/`MAX_ALT` in metres compared with feet, the Kalman filter always being given an altitude).

Issues and corrections are welcome, especially where this tooling disagrees with your results.
